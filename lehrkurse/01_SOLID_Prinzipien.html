Prinzipien für änderbaren Code

SOLID Prinzipien

Dein Code funktioniert heute. Die eigentliche Frage ist: Funktioniert er in sechs Monaten auch noch, wenn eine neue Anforderung dazukommt? SOLID sind fünf Faustregeln, die genau das beeinflussen — nicht als akademische Pflichtübung, sondern als Antwort auf die Frage, warum Code mit der Zeit immer schwerer änderbar wird.

Kapitel 0 · Einstieg

Warum überhaupt Prinzipien?

Fast jedes Softwareprojekt startet schnell und sauber. Nach ein paar Monaten wird jede kleine Änderung zum Drahtseilakt: eine Zeile anpassen, und an drei anderen Stellen bricht etwas. Das ist kein Schicksal — es ist meistens das Ergebnis von fünf immer gleichen Fehlern beim Klassenentwurf.

SOLID ist ein Akronym für fünf Prinzipien, die Robert C. Martin aus genau diesen wiederkehrenden Fehlern destilliert hat. Sie sind keine Regeln, die man stur immer maximal anwendet — sie sind ein Werkzeug, um zu erkennen, an welcher Stelle ein Entwurf wahrscheinlich Ärger machen wird, wenn sich eine Anforderung ändert:

  • S — Single Responsibility Principle
  • O — Open/Closed Principle
  • L — Liskov Substitution Principle
  • I — Interface Segregation Principle
  • D — Dependency Inversion Principle
💡
Aha: Jedes der fünf Prinzipien beantwortet dieselbe Grundfrage aus einem anderen Blickwinkel: Was passiert mit diesem Code, wenn sich etwas ändert? Deshalb zeigt dieses Modul zu jedem Prinzip ein Vorher/Nachher-Beispiel — der Unterschied wird erst beim Ändern sichtbar, nicht beim ersten Lesen.
Kapitel 1 · Single Responsibility
S Single Responsibility Principle: Eine Klasse sollte nur einen einzigen Grund haben, sich zu ändern.

Ein Änderungsgrund pro Klasse

„Verantwortlichkeit" heißt hier nicht „eine Methode" oder „eine Zeile Code" — es heißt ein Änderungsgrund. Wenn eine Klasse aus zwei unabhängigen Gründen geändert werden könnte (z. B. weil sich die Rabattregeln ändern oder weil sich das Druck-Layout ändert), dann hat sie zwei Verantwortlichkeiten — auch wenn sie nur eine Methode dafür pro Aufgabe besitzt.

Ein klassisches Beispiel: eine Rechnung-Klasse, die berechnet, druckt und speichert.

Vorher — drei Gründe, sich zu ändern
class Rechnung {
    double berechneGesamtbetrag() { ... }

    void drucken() {
        double betrag = berechneGesamtbetrag();
        // Layout-Logik fuer den Ausdruck ...
    }

    void speichern() {
        double betrag = berechneGesamtbetrag();
        // SQL-Statement bauen und ausfuehren ...
    }
}
Nachher — drei Klassen, drei Gründe
class Rechnung {
    // nur Daten: Kunde, Positionen ...
}

class RechnungsBerechner {
    double berechneGesamtbetrag(Rechnung r) { ... }
}

class RechnungsDrucker {
    void drucken(Rechnung r, double betrag) { ... }
}

class RechnungsSpeicher {
    void speichern(Rechnung r, double betrag) { ... }
}

Der Gewinn zeigt sich nicht beim Lesen, sondern beim Ändern: Wechselt das Buchhaltungsteam die Steuerlogik, ändert sich nur RechnungsBerechner. Ändert das Design-Team das PDF-Layout, ändert sich nur RechnungsDrucker. Keine der beiden Änderungen kann versehentlich die jeweils andere Verantwortlichkeit kaputt machen.

🚩
Häufiges Missverständnis: SRP heißt nicht „eine Klasse darf nur eine Methode haben". Eine Klasse mit zehn Methoden kann trotzdem SRP-konform sein, solange alle zehn demselben Änderungsgrund dienen (z. B. alle rund um „Berechnung").

Eine Klasse Mitarbeiter berechnet das Gehalt, formatiert den Ausdruck des Gehaltszettels und schreibt Änderungen direkt in eine Datenbank-Tabelle. Ein Kollege sagt: „Das ist doch okay, es geht ja immer um denselben Mitarbeiter." Was ist die treffendste Erwiderung?

  • Nicht das Thema zählt: Gehaltsregeln, Ausdruck-Layout und Datenbankschema ändern sich unabhängig und aus verschiedenen Gründen.
  • Stimmt, solange nur eine Klasse existiert, bleibt der Code automatisch übersichtlich und leichter testbar.
  • Das Problem entsteht erst, wenn eine Klasse mehr als drei Methoden besitzt, vorher greift SRP noch nicht.
  • SRP betrifft nur öffentliche Klassen, interne Hilfsklassen dürfen ruhig mehrere Aufgaben übernehmen.
Kapitel 2 · Open/Closed
O Open/Closed Principle: Offen für Erweiterung, geschlossen für Änderung.

Neues Verhalten hinzufügen, ohne Altes anzufassen

Ein typisches Warnsignal für eine OCP-Verletzung: eine switch- oder if/else-Kette über einen „Typ", die bei jeder neuen Variante um einen weiteren Fall ergänzt werden muss.

Vorher — switch über den Typ
double berechnePreis(String typ, double preis) {
    switch (typ) {
        case "STANDARD": return preis;
        case "STUDENT":  return preis * 0.90;
        case "VIP":      return preis * 0.80;
        default: throw new IllegalArgumentException();
    }
}
// Neue Rabattart "NEUKUNDE"? -> diese Methode
// MUSS geaendert werden, obwohl sie fuer die
// bestehenden drei Faelle schon fertig war.
Nachher — Polymorphismus
interface Rabatt {
    double berechnePreis(double preis);
}
class StandardRabatt implements Rabatt {
    public double berechnePreis(double p) { return p; }
}
class StudentenRabatt implements Rabatt {
    public double berechnePreis(double p) { return p * 0.90; }
}
// Neue Rabattart? -> neue Klasse dazu.
// Keine bestehende Klasse wird angefasst.

Der Unterschied ist konkret messbar: Im „Vorher" wächst eine einzige Methode mit jeder neuen Rabattart und muss jedes Mal neu getestet werden — auch die längst funktionierenden Fälle. Im „Nachher" kommt nur eine neue, isolierte Klasse dazu; alle bestehenden Klassen und ihre Tests bleiben unberührt.

🔭
Diese Aufteilung in austauschbare Klassen mit gemeinsamer Schnittstelle hat einen Namen: das Strategy-Pattern. Modul 02 zeigt dir dieses und weitere Muster im Detail — OCP ist die Motivation, Strategy ist eines der Werkzeuge dafür.

Lückentext — ergänze die fehlenden Begriffe:

Das Single Responsibility Principle verlangt: eine Klasse darf nur einen einzigen haben. Das Open/Closed Principle verlangt: Code soll offen für sein, aber geschlossen für . Die klassische Lösung dafür ist, eine -Verzweigung durch zu ersetzen.

Kapitel 3 · Liskov Substitution
L Liskov Substitution Principle: Ein Subtyp muss sich überall dort einsetzen lassen, wo sein Basistyp erwartet wird — ohne das Verhalten zu brechen.

Vererbung ist ein Vertrag, keine Formalität

Das klassische Beispiel: Pinguin erbt von Vogel, weil ein Pinguin biologisch ein Vogel ist. Vogel hat eine Methode fliegen() — die jede Unterklasse automatisch mit erbt. Ein Pinguin kann aber nicht fliegen.

Vorher — der Vertrag bricht
class Vogel {
    String fliegen() {
        return "fliegt.";
    }
}
class Pinguin extends Vogel {
    @Override
    String fliegen() {
        throw new UnsupportedOperationException(
            "Pinguine koennen nicht fliegen!");
    }
}

// Irgendwo im Code:
for (Vogel v : alleVoegel) {
    System.out.println(v.fliegen()); // kracht bei Pinguin
Nachher — der Vertrag passt zur Realität
abstract class Vogel { /* gemeinsame Basis */ }

interface Flugfaehig {
    String fliegen();
}

class Sperling extends Vogel implements Flugfaehig {
    public String fliegen() { return "fliegt."; }
}

class Pinguin extends Vogel {
    // hat gar keine fliegen()-Methode mehr,
    // dafuer z.B. schwimmen()
}

Was konkret bricht, wenn man den „Vorher"-Code verwendet: Jede Methode, die eine Vogel-Referenz entgegennimmt und fliegen() aufruft, verlässt sich auf den Vertrag „gibt einen String zurück". Ein Pinguin-Objekt bricht diesen Vertrag zur Laufzeit mit einer Exception — der aufrufende Code konnte das nicht wissen, weil er nur mit dem Basistyp Vogel gearbeitet hat. Im „Nachher" gibt es diese Methode bei Pinguin gar nicht erst: Ein Aufruf wäre ein Kompilierfehler, kein Laufzeitfehler.

🚩
Das gleiche Muster tritt bei Quadrat extends Rechteck auf: Wenn setBreite() bei einem Quadrat automatisch auch die Höhe mitändert, bricht das die Erwartung „Breite und Höhe sind unabhängig", die jeder Code hat, der nur mit Rechteck arbeitet.

Eine Klasse Rechteck hat unabhängige Methoden setBreite(int b) und setHoehe(int h). Eine Unterklasse Quadrat überschreibt beide so, dass sie immer beide Seiten gleichzeitig setzen. Welche Aussagen treffen zu? (mehrere richtig)

  • Ein Test, der nach setBreite(5) erwartet, dass getHoehe() unverändert bleibt, schlägt für ein Quadrat-Objekt fehl, obwohl er für Rechteck bestand.
  • Code, der mit einer Rechteck-Referenz arbeitet, kann durch ein Quadrat-Objekt anderes Verhalten bekommen als erwartet — das verletzt LSP.
  • Das Problem lässt sich vollständig lösen, indem man die Klasse Quadrat als private deklariert.
  • Da ein Quadrat mathematisch ein Spezialfall eines Rechtecks ist, ist die Vererbung hier immer korrekt modelliert.
Kapitel 4 · Interface Segregation
I Interface Segregation Principle: Kleine, passgenaue Interfaces statt eines fetten „God-Interface".

Niemand sollte implementieren müssen, was er nicht braucht

Ein Interface Drucker mit print(), scan() und fax() passt gut zu einem teuren Multifunktionsgerät. Ein einfacher Tintenstrahldrucker kann aber nur drucken.

Vorher — ein fettes Interface
interface Drucker {
    String drucken(String dok);
    String scannen(String dok);
    String faxen(String dok, String nr);
}

class Tintenstrahldrucker implements Drucker {
    public String drucken(String dok) {
        return "Gedruckt: " + dok;
    }
    public String scannen(String dok) {
        throw new UnsupportedOperationException();
    }
    public String faxen(String dok, String nr) {
        throw new UnsupportedOperationException();
    }
}
Nachher — passgenaue Interfaces
interface Druckbar { String drucken(String dok); }
interface Scanbar  { String scannen(String dok); }
interface Faxbar   { String faxen(String dok, String nr); }

class Tintenstrahldrucker implements Druckbar {
    public String drucken(String dok) {
        return "Gedruckt: " + dok;
    }
    // keine scannen()/faxen()-Attrappe mehr noetig
}

class Multifunktionsdrucker
        implements Druckbar, Scanbar, Faxbar { ... }

Der „Vorher"-Zustand zwingt jede einfache Implementierung, zwei Methoden vorzutäuschen, die sie gar nicht anbieten kann — mit leeren Rümpfen oder, schlimmer, mit Exceptions, die erst zur Laufzeit auffliegen. Jeder Aufrufer, der nur eine Drucker-Referenz sieht, kann nicht erkennen, welche Methoden tatsächlich sicher aufrufbar sind.

Ein neues Interface Zahlungsmethode verlangt bezahlen(), stornieren() und ratenplanErstellen(). Eine Klasse Barzahlung implementiert bezahlen() sinnvoll, aber stornieren() und ratenplanErstellen() werfen beide eine Exception. Was ist laut ISP der bessere Weg?

  • Das Interface in kleinere Interfaces aufteilen, z. B. Bezahlbar, Stornierbar, Ratenfaehig, sodass Barzahlung nur implementiert, was tatsächlich passt.
  • Die Exceptions durch leere, gut kommentierte Methodenrümpfe ersetzen, damit wenigstens kein Laufzeitfehler mehr auftritt.
  • Eine abstrakte Basisklasse einführen, die stornieren() und ratenplanErstellen() bereits mit Standardverhalten vorgibt.
  • Barzahlung so lassen wie sie ist, da nur ein kleiner Teil der Anwendung diese Methoden überhaupt aufruft.
Kapitel 5 · Dependency Inversion
D Dependency Inversion Principle: High-Level-Module hängen von Abstraktionen ab, nicht von konkreten Low-Level-Klassen.

Wer hängt von wem ab?

„High-Level" ist hier die Geschäftslogik (z. B. „einen Kunden benachrichtigen"), „Low-Level" ist die konkrete Technik (z. B. „eine E-Mail über SMTP verschicken"). Wenn die High-Level-Klasse eine Low-Level-Klasse direkt mit new erzeugt, hängt die wichtige Geschäftslogik von einem austauschbaren Implementierungsdetail ab — nicht umgekehrt, wie man erwarten würde.

Vorher/Nachher: wer hängt von wem ab

Im „Vorher" kennt die High-Level-Klasse die konkrete Low-Level-Klasse beim Namen (durchgezogener Pfeil, rot = eng gekoppelt). Im „Nachher" hängen High-Level-Klasse und beide Low-Level-Klassen von derselben Abstraktion ab (grün = entkoppelt) — die gestrichelten Pfeile stehen für „implementiert das Interface".

Vorher — direkte Abhängigkeit
class Benachrichtigungsdienst {
    private EmailVersender versender
        = new EmailVersender();

    String benachrichtige(String empf, String txt) {
        return versender.senden(empf, txt);
    }
}
// SMS statt E-Mail? -> diese Klasse aendern.
Nachher — Abhängigkeit von der Abstraktion
interface Nachrichtenversender {
    String senden(String empf, String txt);
}

class Benachrichtigungsdienst {
    private final Nachrichtenversender versender;

    Benachrichtigungsdienst(Nachrichtenversender v) {
        this.versender = v; // von aussen uebergeben
    }
    String benachrichtige(String empf, String txt) {
        return versender.senden(empf, txt);
    }
}

Diese Technik — die Abhängigkeit von außen über den Konstruktor hineinzureichen, statt sie selbst zu erzeugen — heißt Dependency Injection. Sie ist die gängigste Methode, DIP in der Praxis umzusetzen, aber DIP selbst ist das Prinzip (wovon hängt der Code ab), Dependency Injection nur eine Technik dafür.

💡
Aha: Der Name „Dependency Inversion" kommt daher, dass sich die übliche Abhängigkeitsrichtung umkehrt. Normalerweise würde man sagen: Low-Level-Details bestimmen, was High-Level-Code tun kann. Hier ist es umgekehrt — die Abstraktion gehört zur High-Level-Seite, und die Low-Level-Klassen richten sich nach ihr.

Zum Abschluss: Ordne jeden Code-Geruch dem Prinzip zu, das er verletzt.

Warum ist „eine Klasse, eine Aufgabe" eine ungenaue Umschreibung von SRP?

Weil „Aufgabe" nach Methodenanzahl klingt. SRP zielt auf Änderungsgründe: Eine Klasse mit zehn eng zusammenhängenden Methoden, die alle aus demselben Anlass geändert werden, ist SRP-konform. Eine Klasse mit zwei Methoden, die aus zwei völlig unabhängigen Gründen geändert werden, verletzt SRP.

Widerspricht OCP nicht der Praxis, dass man Code doch ab und zu ändern muss?

Nein. OCP schließt Bugfixes oder das Ändern von bestehendem, fehlerhaftem Verhalten nicht aus — es geht um den Fall „eine neue Variante kommt dazu" (neue Rabattart, neuer Zahlungsweg). Ziel ist, dass genau dieser Fall keine Kaskade von Änderungen an bereits funktionierendem Code auslöst.

Ist DIP dasselbe wie Dependency Injection?

Nein, auch wenn beide oft zusammen genannt werden. DIP ist das Prinzip: Code soll von Abstraktionen abhängen, nicht von konkreten Klassen. Dependency Injection ist eine Technik, um das umzusetzen — Abhängigkeiten werden von außen hineingereicht (z. B. über den Konstruktor), statt sie selbst mit new zu erzeugen.
