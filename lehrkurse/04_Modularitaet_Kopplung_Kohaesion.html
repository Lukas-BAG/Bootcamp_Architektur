Modularität

Modularität, Kopplung & Kohäsion

Modul 03 hat dir gezeigt, wie man ganze Systeme in Schichten oder Ports & Adapter gliedert. Dieses Modul zoomt eine Ebene tiefer: Wie schneidest du die Module innerhalb einer Architektur so, dass eine einzelne fachliche Änderung an einer Stelle bleibt — statt sich durch die halbe Codebasis zu fressen?

Kapitel 0 · Einordnung

Warum reicht "die richtige Architektur" allein nicht?

Du kannst in Modul 03 die sauberste Schichtenarchitektur oder Hexagonal-Architecture aufgesetzt haben — und trotzdem nach ein paar Monaten ein unwartbares System haben. Wie geht das zusammen?

Eine Architektur legt die groben Bausteine und ihre Beziehungen fest: Web-Schicht, Domänen-Schicht, Persistenz-Schicht; oder Ports und Adapter. Aber innerhalb jeder dieser Schichten entstehen ständig neue Klassen und Module. Ob diese Module gut geschnitten sind — ob verwandte Dinge zusammenbleiben und unabhängige Dinge sich nicht gegenseitig im Weg stehen — entscheidet sich auf einer Ebene, die eine Architekturskizze gar nicht zeigt.

💡
Aha: Architektur beantwortet "in welche groben Teile zerlegen wir das System?". Modularität beantwortet "wie schneiden wir jeden dieser Teile weiter, damit er selbst wartbar bleibt?". Eine gute Antwort auf die erste Frage schützt dich nicht vor einer schlechten Antwort auf die zweite.
Kapitel 1 · Kohäsion

Hohe Kohäsion: was zusammengehört, soll auch zusammen liegen

Kohäsion beschreibt, wie stark die Dinge innerhalb eines Moduls fachlich zusammengehören. Hohe Kohäsion heißt: Wenn du dir die Klasse ansiehst, ergibt sie als Ganzes einen einzigen, klaren Sinn.

Ein sehr häufiges Symptom niedriger Kohäsion ist die "Utils"- oder "Helper"-Klasse: eine Sammelstelle für Methoden, die nichts miteinander zu tun haben, außer dass niemand wusste, wohin damit.

Niedrige Kohäsion
// Utils: drei fachlich fremde Aufgaben in einer Klasse public class Utils { public static String formatDate(Date d) { /* ... */ } public static void sendEmail(String to, String body) { /* ... */ } public static double calculatePrice(Order o) { /* ... */ } }
Hohe Kohäsion
// Drei fokussierte Klassen statt einer Sammelklasse public class DatumsFormatter { public String format(Date d) { /* ... */ } } public class Mailversand { public void send(String to, String body) { /* ... */ } } public class Preisrechner { public double calculate(Order o) { /* ... */ } }

Der Unterschied ist nicht Geschmack, sondern Konsequenz: Ändert sich die Mehrwertsteuer-Berechnung, muss in der rechten Variante nur Preisrechner angefasst werden. In der linken Variante liegt die Änderung in einer Klasse, die auch für E-Mail-Versand zuständig ist — jede Änderung an Utils zwingt dich, den ganzen unübersichtlichen Rest im Kopf mitzudenken, obwohl er gar nicht betroffen ist.

⚠️
Kohäsion ist keine Frage der Klassengröße. Eine große Klasse mit zwanzig Methoden, die alle zur selben Fachlichkeit gehören (z. B. alles rund um eine Bestellung), kann hoch kohäsiv sein. Eine winzige Klasse mit zwei fachlich fremden Methoden ist trotzdem niedrig kohäsiv.

Eine Klasse Utils enthält die Methoden formatDate(Date d), sendEmail(String to, String body) und calculatePrice(Order o) — drei fachlich unabhängige Aufgaben in einer Klasse. Was zeigt dieses Beispiel?

  • Niedrige Kohäsion, denn die drei Methoden haben fachlich nichts miteinander zu tun.
  • Hohe Kohäsion, weil statische Methoden automatisch gut wiederverwendbar sind.
  • Enge Kopplung, da die Klasse gleichzeitig von drei fremden Modulen abhängig ist.
Kapitel 2 · Kopplung

Lose Kopplung: Module sollen möglichst wenig übereinander wissen

Kopplung beschreibt, wie stark ein Modul von einem anderen abhängt — wie viel es über dessen Innenleben wissen muss, damit alles funktioniert. Es gibt eine ganze akademische Taxonomie von Kopplungsarten; für den Alltag reichen zwei Unterscheidungen, die wirklich etwas verändern.

1. Kopplung über konkrete Klassen vs. über Interfaces

Wenn Modul A direkt eine konkrete Klasse aus Modul B erzeugt und aufruft, ist A an jede Detailentscheidung von B gebunden. Programmiert A stattdessen gegen ein Interface, das B anbietet, kann sich die Implementierung hinter dem Interface ändern, ohne dass A etwas davon merkt.

Kopplung an konkrete Klasse
MySqlKundenRepository repo = new MySqlKundenRepository(); repo.findeKunde(id);
Kopplung über Interface
KundenRepository repo = KundenRepositoryFactory.create(); repo.findeKunde(id);

2. Kopplung über viele Einzelparameter vs. über ein klar definiertes Objekt

Eine Methode mit sechs Einzelparametern zwingt jeden Aufrufer, die exakte Reihenfolge und Bedeutung jedes Parameters zu kennen — und jede neue Angabe (z. B. eine zusätzliche Adresszeile) ändert die Signatur überall. Fasst man zusammengehörige Werte stattdessen in einem Objekt zusammen, ändert sich die Methodensignatur nicht mehr, nur das Objekt wächst.

Viele Einzelparameter
void versende(String strasse, String plz, String ort, String land, String name, String telefon) { /*...*/ }
Ein Objekt
void versende( Lieferadresse adresse) { /* ... */ }

Beide Muster laufen auf dasselbe Prinzip hinaus: lose Kopplung heißt, dass ein Modul nur an eine stabile, minimale Schnittstelle gebunden ist — nicht an alle Details, die dahinterstecken.

Welche der folgenden Situationen sind Beispiele für enge Kopplung zwischen zwei Modulen? (mehrere richtig)

  • Ein Modul erzeugt direkt eine konkrete Klasse aus einem anderen Modul statt eines Interfaces.
  • Eine Methode verlangt sechs einzelne Parameter, die eigentlich zusammengehörige Felder eines Kunden sind.
  • Ein Modul ruft eine Methode über ein klar definiertes Interface des anderen Moduls auf.
  • Zwei Module werden unabhängig voneinander in unterschiedlichen Versionen ausgeliefert und betrieben.
Kapitel 3 · Abhängigkeitsrichtung

Abhängigkeiten zeigen auf Abstraktionen, nicht auf Details

Das ist dir nicht fremd: In Modul 01 hast du das Dependency Inversion Principle kennengelernt — hochrangige Module sollen nicht von niedrigrangigen Modulen abhängen, sondern beide von Abstraktionen. In Modul 03 hast du gesehen, wie Hexagonal Architecture genau das auf Systemebene erzwingt: der Domänenkern kennt nur Ports (Interfaces), nie konkrete Adapter.

Genau dasselbe Prinzip gilt jetzt auf Modulebene, nicht nur zwischen Schichten oder einzelnen Klassen: Ein fachliches Modul sollte auf stabile Abstraktionen zeigen — Interfaces, gemeinsame Domänenbegriffe, klar definierte Schnittstellen — und nicht auf volatile Implementierungsdetails, die sich häufig ändern (konkrete Datenbank-Zugriffe, externe API-Clients, technische Hilfsklassen eines anderen Moduls).

🧭
Merkregel: Volatile Dinge (Details, die sich oft ändern) sollen von stabilen Dingen (Abstraktionen, die sich selten ändern) abhängen — nie umgekehrt. Zeigt ein stabiles Modul auf ein volatiles Detail, reißt jede Detail-Änderung das stabile Modul mit.
Warum ist "stabil" hier nicht dasselbe wie "wichtig"?

Weil Stabilität etwas über die Änderungshäufigkeit aussagt, nicht über die fachliche Bedeutung. Ein Zahlungsdienstleister-API-Client kann fachlich extrem wichtig sein — und trotzdem volatil, weil sich API-Verträge, SDKs und Versionen ändern. Genau deshalb sollte die Domänenlogik nicht direkt an diesen Client gekoppelt sein, sondern an ein stabiles Interface, hinter dem der Client austauschbar bleibt.

Kapitel 4 · Zyklische Abhängigkeiten

Zyklische Abhängigkeiten: wenn niemand mehr allein verstanden werden kann

Eine zyklische Abhängigkeit entsteht, wenn Modul A von Modul B abhängt — und B gleichzeitig, direkt oder über Umwege, wieder von A. Damit ist der Kreis geschlossen: A→B→A.

Das klingt harmlos, ist es aber nicht. Sobald ein Zyklus existiert, verschmelzen A und B faktisch zu einem einzigen, größeren Modul — nur dass niemand das so benannt hat:

  • Du kannst A nicht mehr verstehen, ohne B zu verstehen, und umgekehrt — die kognitive Last verdoppelt sich mindestens.
  • Du kannst A nicht mehr isoliert testen, weil ein Test von A automatisch echtes (oder gemocktes) Verhalten von B mitschleppt.
  • Du kannst A nicht mehr austauschen oder unabhängig deployen, ohne B mit anzufassen.

Die Auflösung folgt fast immer demselben Muster: Man extrahiert genau den Teil, den beide Seiten wirklich voneinander brauchen, in ein drittes, neutrales Modul — eine gemeinsame Abstraktion, von der beide ursprünglichen Module abhängen dürfen, ohne dass ein Zyklus entsteht. Manchmal reicht es auch, eine der beiden Abhängigkeiten einfach umzukehren oder ganz zu entfernen, weil sie beim genauen Hinsehen gar nicht nötig war.

Vorher — zyklisch

4 Module, 7 Abhängigkeiten, 3 davon zyklisch (Doppelpfeile). Bestellung ist mit allen anderen wechselseitig verflochten.

Nachher — azyklisch

5 Module (inkl. neuem Kundenreferenz-Interface), 4 Abhängigkeiten, jede zeigt nur in eine Richtung — kein Pfeil führt zurück.

🚩
Genau dieses Muster — Bestellung und Kunde über eine gemeinsame Kundenreferenz-Abstraktion entkoppeln — baust du gleich in der Übung code/04-modularitaet selbst nach.
Ist jede Abhängigkeit zwischen zwei Modulen automatisch ein Problem?

Nein. Abhängigkeiten sind normal und notwendig — kein System besteht aus komplett isolierten Modulen. Problematisch wird es erst, wenn eine Abhängigkeit zyklisch ist oder auf ein volatiles Detail statt auf eine stabile Abstraktion zeigt (siehe Kapitel 3). Eine einseitige, klare Abhängigkeit auf eine stabile Schnittstelle ist völlig gesund.

Kapitel 5 · Modul-Schnitt

Module nach Fachlichkeit schneiden, nicht nach Technik

Die letzte große Design-Entscheidung ist: Entlang welcher Linie schneidest du dein System überhaupt in Module? Zwei Optionen kommen in der Praxis ständig vor — und nur eine davon hält fachliche Änderungen lokal.

Schnitt nach Fachlichkeit (Business-Fähigkeiten)

Modul bestellung enthält alles rund um Bestellungen: Controller, Domänenlogik und Datenzugriff für Bestellungen. Modul kundenverwaltung enthält entsprechend alles rund um Kunden. Ändert sich eine Regel zur Bestellstornierung, betrifft das ausschließlich das Modul bestellung.

Schnitt nach Technik (quer über alle Fachlichkeiten)

Ein Modul controller enthält die Controller aller Fachlichkeiten, ein Modul repository enthält alle Datenbankzugriffe. Ändert sich dieselbe Regel zur Bestellstornierung, musst du jetzt in drei riesigen, fachlich gemischten Modulen je eine Stelle finden und anfassen — und dabei aufpassen, nichts anzufassen, was zu Kunden, Produkten oder Versand gehört.

Der technische Schnitt fühlt sich anfangs ordentlich an — "alle Controller an einem Ort" klingt nach Struktur. Das Problem zeigt sich erst, wenn eine fachliche Änderung ansteht: Sie verteilt sich über alle technischen Module gleichzeitig, während bei einem fachlichen Schnitt dieselbe Änderung in einem einzigen Modul bleibt.

Warum löst eine ordentlich formatierte "Utils"-Klasse kein Kohäsionsproblem?

Weil Formatierung und Sauberkeit im Kleinen nichts über den fachlichen Zusammenhang der Methoden aussagen. Kohäsion ist eine Frage des Inhalts, nicht des Stils: Drei sauber geschriebene, aber fachlich fremde Methoden bleiben fachlich fremd, egal wie ordentlich sie aussehen.

Reicht "wir haben ein Interface eingeführt" allein, um lose Kopplung zu garantieren?

Nein. Ein Interface hilft nur, wenn es so geschnitten ist, dass es genau das zeigt, was der Aufrufer wirklich braucht — nicht die komplette Methodenliste der bisherigen konkreten Klasse. Ein "Interface", das 1:1 alle Methoden einer einzigen Implementierung kopiert, ist oft nur ein Etikett, das die enge Kopplung versteckt, statt sie aufzulösen.

Ist ein technischer Modul-Schnitt (alle Controller, alle Repositories) grundsätzlich falsch?

Nicht grundsätzlich — für sehr kleine Systeme mit wenig fachlicher Komplexität kann er einfacher sein. Er wird zum Problem, sobald das System wächst: Dann verteilt sich jede fachliche Änderung zuverlässig über mehrere technische Module, während ein fachlicher Schnitt dieselbe Änderung lokal hält.
