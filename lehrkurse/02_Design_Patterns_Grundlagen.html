Design Patterns

Design Patterns Grundlagen

SOLID sagt dir, wie guter Code aussieht. Design Patterns sind fertige, bewährte Antworten auf wiederkehrende Entwurfsprobleme — benannte Lösungsschemata, die du nicht neu erfinden musst. Dieses Modul zeigt dir fünf Klassiker im Detail und eine Warnung vor dem sechsten.

Kapitel 0 · Einstieg

Was ist ein Design Pattern eigentlich?

Ein Design Pattern ist ein benanntes, wiederverwendbares Lösungsschema für ein wiederkehrendes Entwurfsproblem — keine fertige Codezeile zum Kopieren, sondern eine Struktur, die du an dein konkretes Problem anpasst. Der Name allein ist schon wertvoll: Sagst du „das ist ein Observer“, verstehen andere Entwickler sofort die Struktur dahinter, ohne dass du sie erklären musst.

🚩
Ein Pattern ist kein Freifahrtschein, es überall einzubauen. Ein Pattern, das kein echtes Problem löst, ist nur zusätzliche Komplexität mit einem hübschen Namen. Die Frage ist nie „Wo kann ich hier ein Pattern anwenden?“, sondern „Welches Problem habe ich gerade — und löst dieses Pattern es besser als der einfache Weg?“

Die „Gang of Four“ (GoF), ein 1994 erschienenes Standardwerk, teilt Patterns in drei Kategorien ein — das reicht hier als Orientierung, ohne es zu vertiefen:

Erzeugend · Creational

Wie Objekte entstehen

  • Factory Method
  • Singleton (mit Vorsicht!)
Strukturell · Structural

Wie Objekte zusammengesetzt werden

  • Adapter
  • Decorator
Verhaltensbezogen · Behavioral

Wie Objekte zusammenarbeiten

  • Strategy
  • Observer
Kapitel 1 · Strategy

Strategy — austauschbares Verhalten statt if/else-Kaskaden

Erinnerst du dich an das Rabattbeispiel aus Modul 01, Kapitel „Open/Closed“? Dort berechnete eine Methode den Rabatt per if/else-Kette über den Kundentyp — jeder neue Kundentyp bedeutete, diese Methode anzufassen und zu riskieren, dass bereits funktionierender Code kaputtgeht. Genau dieses Problem löst Strategy.

Die Idee: Jede Regel wird eine eigene, kleine Klasse, die eine gemeinsame Schnittstelle implementiert (hier RabattStrategy mit der Methode rabattBetrag(betrag)). Der Warenkorb — der „Kontext“ — kennt nur diese Schnittstelle und hält eine Referenz auf die aktuell gewählte Strategie. Neue Rabattarten kommen als neue Klasse hinzu, ohne den Warenkorb zu ändern.

Live: derselbe Warenkorb, unterschiedliche Strategie

Der Bestellwert bleibt bei 200 € gleich — nur die Strategie wechselt, die in den Warenkorb „eingesteckt“ ist. Der Warenkorb selbst enthält dafür keine einzige if/else-Zeile.

💡
Aha: Strategy ist im Kern nichts anderes als „eine Funktion als Objekt verpacken, damit man sie austauschen kann“. In Sprachen mit echten Funktionsreferenzen (Lambdas) wirkt das Pattern manchmal wie unnötiges Zeremoniell — das Grundprinzip (austauschbares Verhalten hinter einer Schnittstelle) bleibt aber dasselbe.

Ein Zahlungsdienst unterstützt Kreditkarte und PayPal. Die Auswahl passiert über eine lange if/else-Kette in der Bestell-Klasse. Welche Änderung entspricht am ehesten der Anwendung des Strategy Patterns?

  • Eine gemeinsame Schnittstelle ZahlungsMethode einführen, mit einer Klasse pro Zahlungsart, und die Bestell-Klasse hält nur eine Referenz auf sie.
  • Alle Zahlungsarten weiterhin in einer einzigen, noch größeren Methode mit mehr else-if-Zweigen zusammenfassen, damit alles an einer Stelle steht.
  • Eine Oberklasse Zahlung einführen, von der KreditkartenZahlung und PayPalZahlung erben, und per instanceof unterscheiden, welche Unterklasse vorliegt.
Kapitel 2 · Factory Method

Factory Method — Objekterzeugung entkoppeln

Factory Method entkoppelt die Erzeugung eines Objekts von seiner konkreten Klasse. Statt überall im Code new PdfDokument() oder new WordDokument() zu schreiben (und bei jeder neuen Dokumentart jede dieser Stellen zu ändern), fragt der aufrufende Code eine DokumentFactory nach einem Dokument und bekommt eines zurück — ohne zu wissen, welche konkrete Klasse dahintersteckt.

Dokument doc = DokumentFactory.erstelleDokument("pdf");
doc.oeffnen(); // der Aufrufer kennt nur die Schnittstelle Dokument

Der Vorteil zeigt sich, sobald ein dritter Dokumenttyp dazukommt (z. B. MarkdownDokument): Nur die Factory wird erweitert, jeder Aufrufer bleibt unverändert.

Welche Aussagen über Factory Method treffen zu? (mehrere richtig)

  • Der aufrufende Code hängt nur von einer gemeinsamen Schnittstelle ab, nicht von den konkreten Klassen dahinter.
  • Neue Produktarten lassen sich hinzufügen, indem nur die Factory erweitert wird — der Aufrufer bleibt unverändert.
  • Factory Method funktioniert nur, wenn alle erzeugten Objekte am Ende exakt dieselbe konkrete Klasse haben.
  • Der Aufrufer muss weiterhin selbst entscheiden, welcher konkrete Konstruktor (PdfDokument oder WordDokument) aufgerufen wird.
Kapitel 3 · Observer

Observer — ein Ereignis, viele Abonnenten

Observer verteilt Ereignisse an mehrere Abonnenten, ohne dass der Sender (das „Subjekt“) jeden Abonnenten im Detail kennt. Reales Beispiel: Ein Warenkorb ändert sich (ein Artikel wird hinzugefügt) — mehrere unabhängige UI-Teile müssen reagieren: die Preisanzeige, die Bestellübersicht, vielleicht eine Versandkostenberechnung. Ohne Observer müsste der Warenkorb jeden dieser Teile einzeln kennen und direkt aufrufen. Mit Observer registrieren sich alle Beobachter über eine gemeinsame Schnittstelle, und der Warenkorb ruft beim Ereignis einfach aktualisieren(...) auf jedem auf.

Live: ein Ereignis, mehrere Beobachter
Status: Bereit

Der Warenkorb (Subjekt, Indigo) kennt seine Beobachter nur über eine gemeinsame Schnittstelle. Grün + Häkchen zeigt an: dieser Beobachter wurde benachrichtigt — er weiß nicht, was die anderen mit der Nachricht tun.

In welchen Szenarien passt Observer gut? (mehrere richtig)

  • Ein Sensor-Wert ändert sich, und mehrere unabhängige Dashboard-Widgets müssen live aktualisiert werden.
  • Ein Nutzer ändert sein Profilbild, Header und Kommentarliste zeigen das neue Bild, ohne sich zu kennen.
  • Ein Taschenrechner soll je nach ausgewählter Eingabe entweder addieren, subtrahieren oder multiplizieren.
  • Eine Datei soll je nach Bedarf wahlweise als PDF-Dokument oder als Word-Dokument geöffnet werden.
Kapitel 4 · Adapter

Adapter — inkompatible Schnittstellen zusammenbringen

Adapter macht zwei Schnittstellen kompatibel, ohne bestehenden Code zu ändern. Beispiel: Eine Alt-Bibliothek liefert Temperaturen über getTemperaturFahrenheit(), dein System erwartet aber überall getTemperaturCelsius(). Die Alt-Bibliothek darfst du nicht anfassen (fremder Code, externe .jar). Ein TemperaturAdapter implementiert die erwartete Schnittstelle und übersetzt intern den Aufruf an die Alt-Bibliothek.

TemperaturSensor sensor = new TemperaturAdapter(altesSystem);
sensor.getTemperaturCelsius(); // rechnet intern: (F - 32) * 5 / 9

Weder die Alt-Bibliothek noch der Code, der TemperaturSensor erwartet, müssen dafür geändert werden — nur die Adapter-Klasse dazwischen ist neu.

Lückentext — ordne die Begriffe richtig zu:

Adapter gehört zur Kategorie der Patterns. Die Klasse, die die inkompatible Alt-Schnittstelle bereitstellt (hier: das alte Temperatursystem), nennt man auch das . Strategy und Observer dagegen gehören zur Kategorie der Patterns, weil sie beschreiben, wie Objekte zur Laufzeit zusammenarbeiten. Factory Method wiederum gehört zur Kategorie der Patterns.

Kapitel 5 · Decorator

Decorator — Verhalten dynamisch erweitern statt Vererbung

Decorator erweitert Verhalten zur Laufzeit, indem es ein Objekt mit einer oder mehreren „Hüllen“ umgibt — statt für jede Kombination eine eigene Unterklasse zu bauen. Klassisches Beispiel: ein Kaffee-Objekt, das mit MilchDecorator, ZuckerDecorator usw. umhüllt wird.

Kaffee bestellung = new ZuckerDecorator(new MilchDecorator(new Espresso()));
bestellung.beschreibung(); // "Espresso, Milch, Zucker"
bestellung.preis(); // 2.00 + 0.50 + 0.20

Die Alternative — eine Unterklasse pro Kombination (KaffeeMitMilch, KaffeeMitZucker, KaffeeMitMilchUndZucker, …) — wächst mit jeder neuen Zutat explosionsartig. Mit Decorator bleibt es bei einer kleinen Klasse pro Zutat, beliebig kombinierbar.

Ordne jedes Pattern dem Problem zu, das es typischerweise löst:

Pattern
Strategy
Factory Method
Observer
Adapter
Decorator
Problem, das es löst
Ich will zur Laufzeit zwischen mehreren Algorithmen wechseln können

Zwei Schnittstellen passen nicht zueinander, ich darf den Altcode nicht ändern

Kapitel 6 · Singleton — Fallstricke

Singleton: der Klassiker, der meistens ein Antipattern ist

Ein Singleton garantiert genau eine Instanz einer Klasse, global über eine statische getInstance()-Methode erreichbar. Das klingt praktisch — ist es aber in den meisten Fällen nicht. Dieses Kapitel ist bewusst eine Warnung, keine Empfehlung.

🚩

Warum Singleton oft schadet:

  • Versteckter globaler Zustand: Jede Klasse kann sich die Instanz einfach holen — Abhängigkeiten werden im Code unsichtbar, statt im Konstruktor sichtbar zu sein.
  • Schwer testbar: Der globale Zustand überlebt zwischen Tests. Ein Test kann von dem beeinflusst werden, was ein anderer Test vorher am Singleton verändert hat — Testergebnisse hängen von der Ausführungsreihenfolge ab.
  • Verdeckte Abhängigkeiten: Eine Methode, die intern Konfiguration.getInstance() aufruft, verrät das nicht in ihrer Signatur — man sieht es erst beim Lesen des Methodenkörpers.

Alternativen: Dependency Injection (die benötigte Instanz wird dem Konstruktor übergeben, statt sie sich selbst zu holen) oder ein expliziter Konstruktoraufruf, bei dem der Aufrufer selbst genau eine Instanz erzeugt und verwaltet, statt sich auf einen globalen Zugriffspunkt zu verlassen. Beides macht Abhängigkeiten sichtbar und Tests unabhängig voneinander — genau das, was die code/02-patterns/singleton-Übung an einem konkreten Beispiel zeigt.

Ein Team nutzt eine Klasse Logger mit statischer getInstance()-Methode als Singleton, die intern alle bisherigen Log-Einträge im Speicher sammelt. Ein Entwickler schreibt einen Unit-Test, der prüft, dass eine Methode genau einen Log-Eintrag erzeugt. Was ist das Hauptproblem dabei?

  • Der Test sieht eventuell Log-Einträge vorheriger Tests, weil alle denselben globalen Zustand teilen — das Ergebnis hängt von der Reihenfolge ab.
  • Singletons lassen sich in Java grundsätzlich nicht mit dem Schlüsselwort static in derselben Klasse kombinieren — das verstößt gegen die Sprache.
  • Der Test wird automatisch spürbar langsamer, weil jeder Aufruf von getInstance() im Hintergrund eine komplett neue Datenbankverbindung öffnet.

Warum ist Strategy trotz ähnlicher Struktur kein Ersatz für Vererbung mit instanceof-Abfragen?

Weil instanceof-Abfragen genau das Problem reproduzieren, das Strategy lösen soll: Der aufrufende Code muss weiterhin jeden konkreten Typ kennen und unterscheiden. Bei Strategy kennt der Kontext nur die gemeinsame Schnittstelle — neue Strategien kommen hinzu, ohne dass irgendwo im Code eine neue Verzweigung entsteht.

Ein Kollege will für jede Kaffee-Variante (Milch, Zucker, Milch+Zucker, ...) eine eigene Unterklasse anlegen. Was schlägst du stattdessen vor?

Decorator: eine kleine Klasse pro Zutat (MilchDecorator, ZuckerDecorator), die ein Kaffee-Objekt umhüllt und dieselbe Schnittstelle behält. Kombinationen entstehen durch Verschachteln der Decorators zur Laufzeit, statt durch eine Unterklasse pro Kombination — das wächst linear statt exponentiell mit jeder neuen Zutat.

Ist Singleton damit grundsätzlich verboten?

Nicht wörtlich verboten, aber die Standardannahme sollte umgekehrt sein: Zeig zuerst, warum eine explizit verwaltete, einzige Instanz oder Dependency Injection nicht reicht, bevor du zu einem globalen getInstance() greifst. In sehr kleinen Skripten ohne Tests mag ein Singleton harmlos sein — in jedem wachsenden, testgetriebenen System wird er fast immer zum Reibungspunkt.
